# 실측 분석·보정 요구사항

- 범위: Figma R01~R11(실측 분석), K01~K04(보정)
- 상위 문서: [기능명세서](../기능명세서.md) ALIGN-01, [API 명세](API_SPEC.md) 8절, [검증 명세](../harness/SPEC.md)
- 이 문서는 **구현할 요구사항 목록**이다. 상태 칸의 "구현"은 main 에 들어가 테스트가 있는 것만 뜻한다. 운영 데이터로 검증했다는 뜻이 아니다.

## 0. 원칙

1. 실측 숫자를 행동 모델에 직접 넣지 않는다. 보정은 **파라미터 배율**만 바꾼다 (AGENTS.md "문제 정답을 행동 모델에 주입하지 않는다").
2. 보정은 **이후 실행에만** 영향을 준다. 끝난 실행·리포트의 예측값은 바꾸지 않는다.
3. 보정 기록은 지우지 않는다. 되돌리기도 새 기록으로 남긴다.
4. 표본이 모자라거나 비교 조건이 다르면 숫자를 만들지 않고 이유를 보여 준다.
5. 가중치·임계치·조정 규칙은 실사용자로 검증하지 않은 가설값이다. 화면과 문서에서 "예측"이 아니라 "가설·모의 결과"로 표기한다.

## 2. 보정 (K01~K04) 요구사항

### 2.1 보정 파라미터 계약

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| CAL-01 | 에이전트 `Persona`에 원인별 가중치 배율 `weight_scale: {원인: 배율}`를 추가한다. 원인 키는 `behavior.CAUSES` 7종. 없으면 1.0 | 스키마 검증(키·범위 0.25~3.0), `PersonaMeter`가 가중치에 곱함, 기본값이면 예전과 같은 결과 |
| CAL-02 | 보정 값은 **세그먼트 단위**로 저장한다. `{"segments": {segment_id 또는 "*": {"threshold_scale": 0.5~2.0, "weight_scale": {원인: 0.25~3.0}}}}`. `"*"`는 전체, 세그먼트 값이 있으면 곱해서 적용 | 범위 밖·모르는 원인·모르는 키는 422. 값은 0.05 단위로 반올림 |
| CAL-03 | 실행을 만들 때 프로젝트의 현재 보정 리비전을 **고정**해 각 페르소나에 반영한다. `frustration_threshold = 60 × threshold_scale`, `weight_scale` 전달. `run.config.calibration_revision`에 기록 | 보정 적용 후 만든 실행만 바뀌고, 이전 실행 입력(TaskRun.input_json)은 그대로. 원인 재현 실행도 같은 규칙 |
| CAL-04 | 리포트·실행 화면에 "보정 rN 적용"을 표시한다 (P05c 확인, P09 실행, P12 리포트) | 보정 없는 실행은 "기본 모형" |

### 2.2 조정안 (K01)

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| CAL-05 | 조정안의 기준은 R08 비교 한 건이다: 기준 리포트 + 매핑 + 기간(기본 7일) + 디바이스(전체) | 응답에 기준(리포트·차수·기간·평균 오차·차이 구간)을 함께 준다 |
| CAL-06 | 조정안은 규칙으로 만든다 (모델 호출 없음, 같은 입력 → 같은 결과) | 아래 규칙 표대로. 단위 테스트로 고정 |
| CAL-07 | 비교 단계의 첫 단계 세션이 100 미만이면 조정안을 만들지 않는다 | `available=false, reason=INSUFFICIENT_SAMPLE` |
| CAL-08 | 차이 구간이 없으면 "조정안 없음"과 이유 | `items=[]`, `reason=NO_GAP` |
| CAL-09 | 각 행은 세그먼트·항목·현재 값·제안 값·근거 문장을 가진다. 바뀌지 않는 세그먼트도 "변화 없음"으로 보여 준다 | Figma K01 표와 같은 열 |
| CAL-10 | 보정 후 오차 | **결정: 다음 실행을 기다린다.** 조정안·적용 화면은 "다음 사전 테스트 후 확인"으로 표시하고, 숫자는 CAL-15 에서 실제 실행으로만 보여 준다 (추정값을 만들지 않음) |

조정 규칙 (v1, 가설):

| 차이 구간 | 대상 세그먼트 | 조정 | 크기 k |
|---|---|---|---|
| 실측 < 예측 하한 (실제로 더 많이 이탈) | 그 단계에서 예측 이탈이 가장 적었던 세그먼트 (리포트 heatmap) | 인내심 임계치 × (1 − k), 그 화면 1위 마찰 원인 가중치 × (1 + k) | k = clamp(\|오차\|/100, 0.05, 0.20), 0.05 단위 |
| 실측 > 예측 상한 (실제로 덜 이탈) | 그 단계에서 예측 이탈이 가장 많았던 세그먼트 | 인내심 임계치 × (1 + k), 1위 원인 가중치 × (1 − k) | 같음 |
| 범위 안 | — | 변화 없음 | — |

- 1위 마찰 원인은 기준 리포트의 화면별 마찰(`/reports/{id}/screens`)에서 그 단계 화면의 가장 많은 세션 원인. 없으면 과업 전체 원인 1위.
- 한 번에 바꾸는 배율은 위 범위로 제한하고, 누적 배율도 CAL-02 범위를 넘지 않는다.

#### 2.4.1 방향 변경 (2026-11-19 결정): 참여자 응답 링크 · "가장 불편했던 화면"

- URL만 있는 고객은 실측 스크립트를 못 넣으므로 **사람 관측이 유일한 검증·보정 근거**다. 그래서 진행자가 옮겨 적는 CSV 보다 **참여자가 직접 답하는 링크**를 주 경로로 한다. CSV 내보내기는 P1, 가져오기는 그 뒤.
- 부탁받은 참여자는 대부분 끝까지 하므로 "어디서 멈췄나"는 정보가 적다. **"가장 불편했던 화면·이유·정도"**를 묻고 모델의 화면별 마찰과 비교한다. 완료 여부는 참고용.
- 참여자는 **타이핑하지 않는다** (모두 누르기). 자유 의견·이름·연락처 칸이 없어 개인정보가 들어올 길이 없다.

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| PART-01 | 담당자가 과업별 참여자 링크를 만든다 (용도 보정용/평가용, 만료 기한, 응답 상한). 복사·끄기 | 로그인 없이 열리는 `/r/{token}`. 끈 링크·만료·상한 초과는 410 |
| PART-02 | 링크 페이지: 과업 안내 → [사이트 열기 ↗] (고객 사이트를 새 탭, 사이트에는 아무것도 넣지 않음) → 질문 4개 → 제출 | 고객 사이트 변경 없음. 참여자 가입·로그인 없음 |
| PART-03 | 질문: ① 끝까지 했나요(완료/그만둠) ② 가장 불편했던 화면 (사전 테스트 화면 캡처 카드에서 고르기, "특별히 없었어요") ③ 이유 (쉬운 문장 7개 + 잘 모르겠어요, 모델 원인 7종에 대응) ④ 불편 정도 1~5 | 모두 선택형. 텍스트 입력 없음 |
| PART-04 | 링크에는 그 과업의 단계 캡처·이름만 보여 준다. 리포트 숫자·다른 과업은 보이지 않는다 | 공개 응답에 예측 수치 없음 |
| PART-05 | 응답은 사람 관측으로 저장한다 (`source=participant_link`, 참여자 코드 자동 R-001…). 같은 브라우저 중복 제출은 막는다 | 응답 상한·속도 제한. IP·user agent 저장 안 함 |
| PART-06 | 비교 지표: **불편 화면 일치**(사람이 고른 화면이 모델 마찰 상위 2개 화면 안), **불편 이유 일치**(그 화면에서 모델이 감지한 원인에 포함), 결과 일치(참고), 불편 정도는 모델 최고 좌절 점수와 나란히 표시(보정에 안 씀) | 분모: 화면을 고른 응답 / 이유를 고른 응답 ("잘 모르겠어요" 제외) |

## 3. API 초안

`/api/v1`, 공통 오류 형식은 API 명세 2절.

| 메서드 / 경로 | 요청 | 응답 |
|---|---|---|
| GET `/projects/{id}/calibration` | — | `{revision: n\|0, params, applied_at, applied_by}` 현재 보정 |
| GET `/projects/{id}/calibration/proposal?days=7` | — | `{available, reason?, basis:{report_id, run_sequence, days, mean_error, gaps:[{stage_id,name,error}]}, items:[{segment_id, segment_name, kind:"threshold"\|"weight", cause?, label, current, proposed, reason}], base_revision}` |
| POST `/projects/{id}/calibrations` | `{expected_revision, items:[...]}` (조정안 행 중 고른 것) | 201 새 리비전 |
| GET `/projects/{id}/calibrations` | `cursor` | `{items:[{id, revision, applied_at, applied_by, changes, base_comparison, error_before_pp, error_after_pp, restored_from}], next_cursor}` (FE `CalibrationRecord`와 같은 이름) |
| POST `/calibrations/{id}/restore` | `{expected_revision}` | 201 새 리비전 |
| GET `/projects/{id}/calibration/compare?revision=n` | — | 단계별 오차 전·후 또는 `reason=WAITING_NEXT_RUN` |
| GET·POST `/projects/{id}/human-observations` | 참여자·과업·결과·단계·원인·용도 | 목록·일치 지표 / 201 |

## 4. 데이터

- `CalibrationRevision(project, revision, params JSON, changes JSON, basis JSON, created_by, created_at, restored_from)` — 프로젝트·리비전 유일, 수정 없음
- `Run.config.calibration_revision` — 실행이 쓴 리비전 번호 (없으면 0)
- `HumanObservation(project, participant_code, task_id, outcome, stage_id, cause, purpose, source, created_at)` — 참여자×과업 유일
