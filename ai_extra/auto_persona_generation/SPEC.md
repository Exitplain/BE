페르소나 생성 자동화 (고정 3프로필 → 타겟 기반 가변 세그먼트)

목적: 고정된 3개 프로필 대신, 사용자가 입력한 타겟 고객 설명·연령 문맥·사이트 분석 결과로 세그먼트와 행동 변수를 생성한다. 생성 결과는 가설이며 보정 전에는 실제 고객 비율로 해석하지 않는다.

현재 하드코딩 (자동화 대상)
- agent/persona_dashboard.py:20 PROFILES — quick / careful / patient 3종 (context, max_required_fields 2/4/6, width 390/1280/1440, search_sensitivity, cost_sensitivity)
- 세션 구조 고정: 프로필 3 × 선택 과업 수, 동시 실행 한도 3, 모의 사이트 한정
- agent/frustration.py — 임계치가 max_required_fields × 16으로 프로필 값에서 직접 파생
- docs/API_SPEC.md — 프로필 `quick, careful, patient`, 세그먼트 수·시드 횟수를 UI에서 보내지 않음
- agent/README.md — "자연어 패널 생성"은 미구현
- Figma P05b — 세그먼트 4개 × 5명 = 20명(예시), 세그먼트 이름 생성 방식·행동 변수 척도(0~100)는 D04 P07 확인 필요

원칙
- 연령·인구통계는 문맥으로만 쓰고 고정관념 묘사를 만들지 않는다 (D04 P03). 연령으로 행동 모델을 보정하지 않는다.
- 생성 변수는 감사 가능한 값(예: 필수 입력 허용 수, 화면 폭, 탐색·비용 민감도)으로 제한하고 범위를 검증한다. 범위 밖 값은 거부한다.
- 세그먼트 합계는 확정 인원과 일치해야 한다. 비율은 보정 전까지 실제 고객 비율이 아니라 가정으로 표시한다.
- 세션별 브라우저·기억·출력 격리를 유지한다. 문제 정답과 퍼널·원인 후보를 페르소나 입력에 넣지 않는다.
- 같은 입력과 시드에서 같은 세그먼트가 나오도록 재현 가능하게 한다. 생성 결과는 revision으로 저장하고 과거 실행을 덮어쓰지 않는다.
- 테스트 계정 수가 있으면 로그인 테스트의 상한이 된다 (P05 "최대 20").

Subagent

- 페르소나 생성 에이전트 1종 (읽기 전용): 타겟 설명·연령 문맥·사이트 분석 요약을 받아 세그먼트 초안을 산출한다.
  - 입력: 타겟 설명, 연령 문맥, 확정된 과업 목록, 총 인원, 허용 변수 범위(스키마)
  - 수정 범위: 없음, 세그먼트 초안만 쓴다
  - 인계 산출물: 세그먼트[{id, name, count, 변수값, 생성 근거}], 범위 검증 결과
- 검증 에이전트는 별도로 두고 스키마·합계·범위·격리만 검사한다. 생성된 행동의 "그럴듯함"을 정답처럼 평가하지 않는다.

SKILL

- 로컬(_local): 타겟 소스 코드를 읽을 수 있을 때, 코드에서 변수 허용 범위를 제안하는 스킬. 과업별 필수 입력 수 분포, 반응형 breakpoint(화면 폭 후보), 로그인·인증 필요 여부를 읽어 `max_required_fields`·`width` 범위로 제안한다. 코드 정보는 범위 제안에만 쓰고 페르소나 행동에 직접 주입하지 않는다. 이후 스키마 검증, 합계·범위 검사, 재현성 검사를 한다.
- URL(_url): 실제 사이트에서는 화면 폭·입력 항목이 알려지지 않으므로 정찰 결과에서 필수 입력 수 분포를 참고하되, 페르소나 변수에는 정찰 결과를 직접 넣지 않고 범위 제안으로만 쓴다. 로그인이 필요하면 등록된 테스트 계정 수 안에서만 생성한다.
- 공통: 이름 붙이기·설명 생성에만 LLM을 쓰고, 변수 값은 스키마가 허용한 범위에서만 받는다. 실제 API 호출은 키·모델·호출 범위를 확인한 뒤에만 실행한다.

Workflow

1. 입력 검증: 타겟 설명(최대 길이 제한), 연령 값(any는 단독), 총 인원, 계정 수 상한을 확인한다.
2. 세그먼트 초안: 타겟 설명에서 세그먼트 후보를 만들고 변수 범위를 스키마로 검증한다.
3. 사용자 확인: 세그먼트 이름·인원을 보여주고 수정(합계 일치)한다. P05b에서 조정, 오류는 P05e 규칙을 따른다.
4. 확정: 합계·범위가 맞으면 revision으로 확정한다. 이후 변경은 새 revision이다.
5. 실행 입력 변환: 변수값을 FrustrationMeter 입력(임계치·민감도)으로 변환한다. 변환 규칙은 코드에 하나로 둔다.
6. 기록: 세그먼트·변수·시드를 실행 기록에 남기고 모델 버전과 보정 revision을 함께 표시한다.

성공 기준 (각 항목은 pass / fail / blocked로 기록)

- [ ] 프로필 수·이름·변수값이 고정 3종이 아니라 입력에서 생성되고 입력에 따라 달라진다
- [ ] 생성된 변수가 모두 허용 범위 안이고 범위 밖 값은 거부된다
- [ ] 세그먼트 합계가 확정 인원과 일치한다 (불일치는 오류로 표시)
- [ ] 같은 입력·시드에서 같은 세그먼트가 재현된다
- [ ] 연령·타겟 설명이 행동 변수를 직접 바꾸지 않는다 (문맥 전용, 테스트로 확인)
- [ ] 세션 간 브라우저·기억·출력 격리가 유지된다
- [ ] 정찰 결과·문제 정답·원인 후보가 페르소나 입력에 포함되지 않는다 (계약·테스트로 확인)
- [ ] 계정이 필요한 테스트에서 계정 수를 초과하는 세그먼트를 만들지 않는다
- [ ] 비율이 보정 전이면 실제 고객 비율이 아니라 가정이라고 표시된다
- [ ] 세그먼트 이름 생성 방식·행동 변수 척도(D04 P07)를 확정했다 (현재 미정)
