# 에이전트 판정(PersonaMeter) 점검 — ROC / AUC

`agent/behavior.py`의 `PersonaMeter`(화면 관측 → 불만 점수 → 이탈·원인)를 브라우저 없이 평가한다. **관측은 이 스크립트가 구성한다.** 따라서 이것은 *구성 타당성*(심어둔 결함을 구분하는가, 엉뚱한 원인에 반응하지 않는가, 정상 잡음에 거짓 경보를 내지 않는가) 점검이며, **실제 사람의 이탈 예측력을 말해주지 않는다.** 높은 AUC는 설계상 쉽게 나오고, 의미 있는 부분은 약한 결함·정상 잡음에서의 거동, 교차 반응, 주원인 정확도다.

## 설계
- 화면 흐름: landing → browse → detail → cart → signup → payment → complete (develop의 7단계 키)
- 정상 세션에도 **무해한 잡음**을 넣는다: 스크롤·재방문, 0.2~2초 응답, 2% 확률의 3초 초과 응답
- 결함 7종(원인 키와 같음) × 강도(mild, strong). 세션마다 페르소나 수치 4개·허용 입력수·시드를 무작위로 뽑는다
- 점수는 `score / threshold`(페르소나마다 임계치가 달라 정규화)를 쓰고, `>= 1`이 에이전트의 실제 이탈 결정이다

## 사전 등록 기준 (실행 전에 작성)
| 항목 | 기준 |
|---|---|
| 이탈 ROC AUC (결함 전체 vs 정상) | ≥ 0.85 |
| 이탈 ROC AUC (mild 결함만 vs 정상) | ≥ 0.70 |
| 원인별 검출기 AUC (해당 원인 vs 나머지 전부, 기여 점수) | 7개 모두 ≥ 0.90 |
| 정상 세션 거짓 경보율 (실제 결정 기준) | ≤ 0.10 |
| 이탈한 결함 세션의 주원인 정확도 | ≥ 0.80 |
| 교차 반응: 해당 원인 외의 검출기가 평균 기여의 30% 이상을 내는 쌍 | 허용 목록(설계상 동시에 켜지는 쌍) 밖에서 0개 |

판정은 pass / fail로 기록하고, 기준 미달이면 그대로 보고한다.

## 결과 run1 (2026-11-15, develop fe72fac의 `agent/behavior.py`) — **fail (1/6 미달)**
증거: `results/run1.json`, `results/meter_roc.png`, `results/meter_dose_detection.png`. 재현: `PYTHONPATH=<repo> python roc_meter.py results` (Python ≥3.11, pydantic·numpy·scikit-learn·matplotlib).
세션 4500개(정상 600 + 결함 7종 × mild/strong × 300), 시드 20261115.

| 기준 (사전 등록) | 결과 | 판정 |
|---|---|---|
| 이탈 ROC AUC, 결함 전체 vs 정상 ≥ 0.85 | **0.805** | **FAIL** |
| 이탈 ROC AUC, mild만 ≥ 0.70 | 0.800 (strong 0.810) | pass |
| 원인별 검출기 AUC 7개 모두 ≥ 0.90 | 최소 0.925 (technical), 나머지 0.9995~1.0 | pass |
| 정상 세션 거짓 경보율 ≤ 0.10 | 0.005 | pass |
| 이탈 시 주원인 정확도 ≥ 0.80 | 0.995 (n=657) — **아래 주의 참고** | pass |
| 교차 반응 쌍 0개 | 0개 | pass |

### 해석
1. **검출기는 동작한다.** 원인별로 결함을 심으면 해당 원인의 기여 점수만 오른다(교차 반응 없음). technical의 0.925는 정상 세션의 2% 무해한 지연 응답에도 검출기가 반응하기 때문이다(이탈 결정에는 영향 없음, 거짓 경보율 0.005).
2. **그러나 이탈 결정은 몇 가지 원인에만 연결돼 있다.** 결함 하나가 단독으로 이탈을 일으키는 비율(mild/strong): input_burden 0.58/0.60, navigation 0.20/0.54, cost 0.11/0.09, trust 0.03/0.03, **value 0/0, technical 0/0, accessibility 0/0.01**. 단일 결함의 가중치(value 20, trust 30, technical 15, accessibility 20, cost 40)가 임계치(60 × 인내심 배율)와 단계 도착 보상(−4)을 넘지 못한다. 실제 이탈 결정 지점(ROC 그림의 빨간 점)의 민감도는 약 0.16이다. 이것이 AUC 0.805의 원인이다.
3. **"주원인 정확도 0.995"는 선택 편향이다.** 이탈한 세션만 대상이라 input_burden·navigation·cost가 거의 전부이고, value·technical은 이탈 사례가 0건이라 평가 자체가 불가능하며 accessibility는 n=3(재현율 0.33)이다. 7개 원인이 정확히 지목된다는 증거가 아니다.
4. **강도(severity)를 표현하지 못한다.** 용량-반응 곡선이 계단형이다: 허용치를 1칸 넘으면 이탈률이 즉시 상승(낮은 인내심 ≈0.97, 높은 인내심 ≈0.30)하고 1칸이든 8칸이든 같다. mild와 strong의 차이가 없는 것도 같은 이유(원인별로 한 번만 점수에 반영).

### 제품에 주는 함의
- 리포트에서 **"이탈 원인"과 "감지된 마찰"을 분리**해야 한다. 이탈 사례만 보면 value·technical·trust·accessibility는 거의 나타나지 않지만, 마찰 신호로는 감지된다.
- 입력 부담의 강도가 반영되지 않으므로 필드 수 초과량이 이탈률 차이로 나타나지 않는다.
- 가중치·임계치는 여전히 사람 데이터 없이 정한 값이다. 이 결과는 그 값이 현실과 맞는지가 아니라 **현재 값이 어떻게 동작하는지**를 보여준다.

### 한계 (통과·실패가 의미하지 않는 것)
- 관측을 직접 구성했으므로 **실제 사람의 이탈 예측력과 무관**하다. 결함 정의와 "무해한 잡음"(스크롤 0~3회, 지연 2%)은 제 가정이다.
- 세션당 결함은 하나만 넣었다. 실제 세션은 여러 마찰이 누적되므로 단독 결함의 낮은 이탈률은 실제보다 비관적일 수 있다(누적 효과는 평가하지 않았다).
- 실제 에이전트 루프(브라우저, 화면 인식, 행동 선택)는 포함하지 않았다. 데모 쇼핑몰(FE 저장소)과 맞는 Chromium이 이 환경에 없었다.
- 기준은 실행 전에 정했고 결과를 보고 바꾸지 않았다.
